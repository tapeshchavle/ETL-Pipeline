# 🐘 PostgreSQL — Analytical Data Warehouse

## Overview

PostgreSQL 15 serves as the **analytical data warehouse** for Foodingo. Unlike MongoDB (which handles live application transactions and document storage), PostgreSQL is purpose-built for **analytical SQL queries** — aggregations, joins, window functions, and time-series reporting.

It acts as the **"Hot Path"** in our Lambda Architecture:
- Storing real-time events ingested by the Kafka Consumer (`raw` schema)
- Hosting business-ready dimensional and fact tables generated by dbt (`analytics` schema)
- Powering fast Metabase dashboards for executive reporting
- Supplying cleaned feature matrices to the Python ML Service

---

## Why PostgreSQL?

| Requirement | How PostgreSQL Solves It |
|---|---|
| **SQL Analytics** | Powerful query engine with window functions, aggregations, and CTEs |
| **JSONB Support** | Can store semi-structured arrays (e.g., `ordered_items`) and index them efficiently |
| **Two-Schema Isolation** | Separate `raw` (append-only ingestion) and `analytics` (clean BI reporting) schemas |
| **Tool Ecosystem** | Natively supported by dbt, Metabase, Airflow, and Python data science libraries |

## 🔬 How PostgreSQL Works Internally in Foodingo

### Step 1: Ingestion into the `raw` Schema

When an event arrives from Kafka, the Python Kafka Consumer executes a parameterized SQL `INSERT` statement into the `raw` schema:

```sql
INSERT INTO raw.order_events (
    event_type, order_id, user_id, user_address, email, phone_number,
    amount, payment_status, order_status, razorpay_order_id, razorpay_payment_id,
    ordered_items, event_timestamp, ingested_at, kafka_topic, kafka_partition, kafka_offset
) VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s, %s, %s, %s::jsonb, to_timestamp(%s), NOW(), %s, %s, %s);
```

**Key Internal Feature — `JSONB` Storage:**
- Notice `ordered_items` is cast to `::jsonb`. 
- Unlike standard text JSON, PostgreSQL's `JSONB` format decomposes the JSON array into binary format on disk.
- This allows indexing and ultra-fast extraction of nested keys (like `foodId` and `price`) later during dbt transformations without needing regex or string parsing.

### Step 2: Nightly Batch Transformation into `analytics` Schema

Every night at **2:00 AM IST**, Apache Airflow triggers `dbt run`. dbt executes SQL against PostgreSQL to build clean reporting tables:
1. **Staging Views (`stg_*`):** dbt executes `CREATE OR REPLACE VIEW analytics.stg_orders AS ...`, applying window functions (`ROW_NUMBER() OVER(PARTITION BY order_id ORDER BY event_timestamp DESC)`) to deduplicate retried events.
2. **Fact Tables (`fact_*`):** dbt executes `CREATE TABLE analytics.fact_orders AS SELECT ...` from the staging views, producing immutable historical records.
3. **Mart Tables (`daily_revenue`, `food_popularity`, etc.):** Pre-aggregated analytical tables are created. For example, `food_popularity` uses PostgreSQL's native `jsonb_array_elements(ordered_items)` to explode the JSON array of items into individual rows and aggregate order counts per food item.

### Downstream Consumers of the `analytics` Schema:
1. **Metabase (`http://localhost:3000`):** Connects via JDBC to `foodingo_warehouse` and executes queries against `analytics.daily_revenue`, `analytics.food_popularity`, etc. The CEO views these dashboards without running raw SQL.
2. **ML Service (`http://localhost:5001`):** 
   - When Airflow triggers `POST /train/recommender`, the ML service queries `analytics.ml_user_order_matrix` to build the user × food collaborative filtering similarity matrix.
   - When Airflow triggers `POST /train/churn`, it queries `analytics.cart_abandonment` to train the logistic regression churn predictor.

## Lambda Architecture: Why Hot Path vs. Cold Path?

In Foodingo's **Lambda Architecture**, PostgreSQL serves as the **Hot Path**:
- It is optimized for sub-second dashboards, operational BI, and recent historical data (e.g., last 1-2 years of orders).
- **The Big Data Limit:** If Foodingo grows to **100 million+ orders**, relational `GROUP BY` queries on PostgreSQL will start slowing down Metabase dashboards and ML training.
- When data exceeds single-node database capacity, heavy historical processing is offloaded to **Apache Spark (the Cold Path)**, which reads immutable Parquet files directly from the AWS S3 Data Lake (`foodingo-data-lake`), crunches the numbers across distributed workers, and writes summarized aggregate metrics back into PostgreSQL for Metabase to display.

## 🚀 Future Scaling Guide

When Foodingo's transaction volume grows, follow this scaling roadmap for PostgreSQL:

### Level 1: Connection Pooling (PgBouncer)
When Metabase users, dbt jobs, and Kafka consumers start competing for database connections:
- Deploy **PgBouncer** as a lightweight connection pooler in front of PostgreSQL.
- Allows thousands of incoming client connections while maintaining a small, optimized pool of physical PostgreSQL connections.

### Level 2: Table Partitioning (Declarative Partitioning)
When `raw.order_events` grows beyond 10 million rows:
- Convert `raw.order_events` to a **partitioned table by month**:
  ```sql
  CREATE TABLE raw.order_events (
      ...
  ) PARTITION BY RANGE (event_timestamp);
  
  CREATE TABLE raw.order_events_2026_07 PARTITION OF raw.order_events
      FOR VALUES FROM ('2026-07-01') TO ('2026-08-01');
  ```
- Queries filtering by date range will scan only the relevant monthly partition.

### Level 3: Read Replicas for BI Dashboards
When analytical queries from Metabase start slowing down real-time ingestion from Kafka:
- Provision a **PostgreSQL Read Replica** (or use Amazon RDS / Aurora Read Replicas in production).
- Point Metabase and the ML Service training jobs to the read replica (`analytics` schema queries), leaving the primary instance dedicated to Kafka ingestion and dbt table materialization.

### Level 4: Offloading Historical Data to Spark
When historical data exceeds several hundred gigabytes:
- Keep only the last 12 months of raw events in PostgreSQL.
- Query historical data (> 1 year old) directly from AWS S3 Parquet files using Apache Spark or AWS Athena.

```bash
# Connect to PostgreSQL interactive shell (psql)
docker exec -it foodingo-postgres psql -U foodingo -d foodingo_warehouse

# List all schemas
docker exec -i foodingo-postgres psql -U foodingo -d foodingo_warehouse -c "\dn"

# List tables in raw and analytics schemas
docker exec -i foodingo-postgres psql -U foodingo -d foodingo_warehouse -c "\dt raw.*"

# Count ingested raw order events
docker exec -i foodingo-postgres psql -U foodingo -d foodingo_warehouse -c "SELECT count(*) FROM raw.order_events;"

# Check daily revenue mart table
docker exec -i foodingo-postgres psql -U foodingo -d foodingo_warehouse -c "SELECT * FROM analytics.daily_revenue ORDER BY revenue_date DESC LIMIT 10;"
```
